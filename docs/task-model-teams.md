# Команда моделей для задачи разработки

В «Задачи → Новая задача» включите «Совет планирования и команда моделей». Для существующей задачи откройте вкладку «Команда»; перед изменением настроек остановите задачу.

1. В разделе «Модели» создайте отдельный профиль каждой нужной модели. Можно добавить несколько моделей Codex, Claude Code или локального сервера.
2. Выберите от двух до шести планировщиков. Номер места определяет очередь в обсуждении. Два одинаковых профиля одной модели одного сервера не считаются двумя участниками.
3. Выберите модель «Оценка завершения обсуждения». По умолчанию — текущая активная модель на момент запуска совета (с учётом автовыбора); отдельная модель фоновых задач не подменяет этот выбор. Оценщик закрепляется до перезапуска обсуждения. При необходимости назначьте разработчика, модель анализа тестов и модель ревью. Пустой разработчик использует обычную модель задач / автовыбор. Назначенный профиль используется напрямую, без скрытой подмены другой моделью.
4. Задайте максимум кругов (1–8, по умолчанию 3) и время обсуждения (30–1800 секунд, по умолчанию 10 минут). Каждый ответ модели расходует её лимит. Круг — обход всех участников; на первый черновик и его подтверждение автором обычно нужно больше одного круга.
5. Нажмите «Начать». Ход и предложения видны во вкладке «Обсуждение плана»; принятый план — во вкладке «План».

## Как принимается план

Модели по очереди получают цель, ограничения, ограниченную выборку контекста проекта, текущую полную редакцию и последние замечания коллег. Планировщики работают только с текстом, без команд и инструментов. Каждая возвращает структурированное «согласен» или полную новую редакцию с обоснованием.

Согласие относится к конкретному хешу плана. Правка сбрасывает прежние голоса; автор новой редакции также должен явно подтвердить её. Пустой, некорректный, просроченный ответ, согласие с другой версией или согласие с блокирующими замечаниями не засчитывается. Начальный черновик сам по себе не считается голосом.

После единогласия оценщик получает цель, контекст, текущий план и протокол замечаний. Он проверяет закрытие существенных замечаний, отсутствие противоречий, наличие критериев готовности и проверок. `complete` с точным хешем, пустым списком незакрытых вопросов и обоснованием разрешает разработку. `continue` с конкретными вопросами возвращает их участникам и сбрасывает голоса: прежнее единогласие не перекрывает замечания оценщика. Оценщик не может единолично утвердить план без голосов участников. Его имя, число проверок и заключение видны в карточке и протоколе.

Проверки оценщика входят в общий лимит времени; их максимум равен числу кругов, запросы считаются отдельно от голосов планировщиков и сохраняются до отправки. Ошибка, неверная версия, пустое/противоречивое решение, истечение времени или смена профиля во время ответа не разрешают разработку. При возобновлении ни оценка, ни её бюджет не сбрасываются. Для обсуждений, созданных до появления оценщика, требуется явный перезапуск совета.

Сейчас оценщик использует обычный текстовый транспорт модели с проверяемым JSON-решением. Специализированные reward-модели с числовым выходом пока не подключены: им нужен отдельный транспорт и проверка порога на размеченных примерах. Высокая оценка качества не равна доказательству закрытия замечаний. Генеративный специализированный оценщик также остаётся языковой моделью; его штатный шаблон ответа может потребовать адаптации.

Кандидаты для отдельного испытания: [Skywork-Reward-V2-Qwen3-4B/8B](https://huggingface.co/Skywork/Skywork-Reward-V2-Qwen3-8B) для числовой оценки качества и [Prometheus 2 7B](https://huggingface.co/prometheus-eval/prometheus-7b-v2.0) для оценки по рубрике с объяснением (карточка указывает английский язык). Их пригодность именно для русских обсуждений планов здесь не измерена. Реранкеры поиска, например Qwen3-Reranker, оценивают релевантность документов запросу и не заменяют проверку консенсуса.

Если лимит кругов или времени исчерпан, задача ставится на паузу с явным «консенсус не достигнут». Обычное возобновление не обнуляет потраченные запросы. «Перезапустить обсуждение» — явный запуск нового бюджета; последняя редакция передаётся как предложение, все голоса собираются заново. Предыдущий протокол сохраняется.

Недоступность участника, окончание его лимита, запрет внешнего подключения или выход за часы модели останавливают этап. Назначенные планировщики не заменяются глобальной резервной моделью: иначе получилось бы согласие другого состава. Поправьте настройки/лимиты или измените команду остановленной задачи.

При перезапуске приложения сохраняются редакция, голоса, число уже отправленных запросов и затраченное время. Смена модели участника во время ответа делает его голос недействительным. Смена состава требует нового обсуждения.

## Разработка и проверки

Разработчик работает обычными инструментами задачи в рабочей копии проекта. Изменения в исходный проект принимаются человеком прежней кнопкой «Принять изменения». Отметки выполненных пунктов не меняют версию согласования. Содержательная правка плана через update_plan запускает новое согласование (не более двух таких автоматических пересмотров подряд). Внешняя правка плана или новые требования не позволяют продолжать исполнение старого согласования.

Настоящие тесты запускает ядро, не модель. Выбранная модель анализа тестов получает результаты, выборку исходников тестов, diff и журнал и проверяет покрытие/выводы. Модель ревью независимо проверяет код и результат. Их заключения доступны во вкладке «Проверки команды». Отклонение возвращается разработчику; ошибка или некорректное заключение останавливают задачу, а не становятся успешной проверкой. Заключения привязаны к состоянию кода, результатам тестов, итоговому тексту и профилю модели; изменение этих данных требует повторной проверки.

Консенсус не заменяет запуск тестов и проверку результата. При обычной задаче без команды сохраняется прежнее поведение.

## Файлы и проверка реализации

В папке задачи сохраняются `обсуждение-плана.json` (полный протокол и состояние), `обсуждение-плана.md` (читаемая история), `проверка-команды.md` (заключения). Прежние обсуждения сохраняются в `_team-history/`. Конфигурация задачи хранит идентификаторы профилей, а не копии ключей авторизации.

Проверки:

- `planning_council_test.py`: точная версия согласия, аннулирование голосов, ограничение кругов/времени, остановка, отсутствие подмены модели, сохранение бюджета, изменение профиля во время ответа, запрет кодовых действий без согласования.
- `task_council_flow_test.py` (также `--bundle`): настоящее ядро, WebSocket и локальные тестовые модели. Две модели изменяют план и согласуют его; отдельный разработчик исправляет код, запускаются настоящие тесты, анализ тестов и ревью выполняют свои модели. Исходный проект остаётся нетронутым. Второй сценарий без согласия не допускает ни одного шага разработки.
- Нативный Cocoa/WebKit smoke: выбор команды, передача ролей при создании, показ отсутствия консенсуса, запрет редактирования работающей задачи, корректная обработка ошибки сохранения.

Платные генерации и пользовательские проекты при приёмке не используются.
