# Минусовка для существующего плеера Dewiar: план реализации

Дата: 4 ноября 2026. Проверенная база: `35b40d4`.
Статус: проектирование; код подготовки минусовок ещё не внедрён.

Основа — [экспертный план, редакция 3](karaoke-plan-2026-11-04.md). Этот документ уточняет его применительно к текущему коду и определяет порядок разработки. [Отдельный экран караоке](karaoke-screen-plan-2026-11-04.md) остаётся отложенным.

## 1. Что поставляем

В «Задачи → Песни» готовим минусовку сохранённого исполнения. Два способа запуска используют один конвейер:

1. Кнопка **«Подготовить минусовку»** в открытой песне; для готовой — повторная подготовка отдельного кандидата.
2. **«Подготовить минусовки»** для выбранных песен; также необязательный этап музыкальной пакетной обработки после получения полноценного аудио.

В существующем плеере — переключатель **«Оригинал / Минусовка»**. Остаются прежние play/pause/stop, переходы по строкам, подсветка слов и прокрутка. Пауза сохраняет позицию. Стоп сбрасывает следующий запуск в начало и сохраняет последнее выделение по действующему поведению. Переключение дорожки сохраняет позицию и намерение пользователя «играть / оставаться на паузе».

По умолчанию удаляем все поющие голоса, включая бэк-вокал. Вариант с сохранённым бэком, звуковая транспозиция, ансамбли и отдельный экран сравнения — после первой работоспособной поставки. Стрелки полутонов по-прежнему изменяют только обозначения аккордов; подсказки не должны обещать изменение высоты звука.

Результат по каждой реальной записи: пригодная к воспроизведению минусовка, либо технически готовый вариант с перечисленными дефектами, либо конкретная причина неудачи. Статус «готова» означает завершение обработки, а оценка музыкального качества хранится отдельно. Отсутствие разборчивого голоса и сохранность гитары проверяем на записи, а не обещаем по названию модели.

## 2. Проверенные факты о текущей установке

Проверка выполнена чтением исходников, метаданных окружения и `ffprobe`, без запуска моделей и изменения рабочих карточек.

| Узел | Сейчас | Следствие для реализации |
|---|---|---|
| `core/songs/review.py::review_command` | `song_full_audio`: исходный файл → MP3 128 кбит/с, 44,1 кГц, стерео → base64; максимум 600 000 мс и 11 500 000 байт | Расширить выбор дорожки; сохранить транспорт и лимит кадра 16 МиБ. Тяжёлое разделение не выполнять в этой команде |
| `ui/studio/song_review.js::bind` | Один `<audio>`, один `fullData`, счётчик `audioRequest`, общие кнопки карточки и листа | Заменить одиночный кэш кэшем вариантов и добавить безопасную смену источника; второго одновременно звучащего плеера не создавать |
| `song_sheet.js` / `playback_layout.py` | Подсветка и переносы есть; часть времён оценочная | Минусовка наследует временную шкалу, не пересчитывает слова и аккорды. Не обещать исправление уже неточных времён |
| `core/songs/analysis.py::SongAnalyzer` | Собственные потоки, отмена, `_heavy_lock`; блокировка охватывает полный внешний разбор, но базовый STT выполняется раньше | Нельзя считать, что все тяжёлые задачи уже сериализованы. Добавить общий шлюз фоновых музыкальных операций |
| `core/songs/store.py` | `patch()` меняет revision карточки и пишет историю; `recover_interrupted()` знает только общий статус песни | Прогресс минусовки хранить отдельно: иначе фоновое обновление будет конфликтовать с правкой текста |
| `core/engine_commands.py` | `song_cancel` отменяет поиск и ASR; нет отмены минусовки | Отдельные команды и события, без вызова `SongAnalyzer.cancel()` для минусовки |
| `core/tasks.py`, `core/media_transcription.py` | Пакетная расшифровка: текст, очистка, резюме; может обойтись субтитрами без скачивания аудио | Для музыкального этапа нужен явный доступ к исходному аудио; очищенный прозаический текст не переносить в песню |
| `tools/song_separation_probe.py` | Эксперимент HTDemucs CPU, кэш `955717e8.safetensors`, результат `mix − vocals` | Использовать как базовую линию; это ещё не промышленный worker с очередью и проверками |
| Окружение | Mac arm64, macOS 27.0.1, 64 ГиБ RAM; `.songs-separation-venv`: torch/torchaudio 2.11.0, demucs 4.0.1; production runtime separation отсутствует | Скорость и пик памяти измерить на этом Mac. Старый экспериментальный runtime не обновлять на месте |

### Реальные исходники

Во всех девяти файлах `ffprobe` показал **PCM signed 16-bit little-endian, 48 000 Гц, 2 канала**. Это формат сохранённой копии, а не доказательство исходного lossless-качества или настоящего стерео. Полоса и корреляция каналов пока не измерены. В карточках частота и каналы не заполнены, длительности нередко округлены; ориентироваться на декодированные сэмплы файла.

| Планы — Владимир Клявин | 204,713250 | Сохранность атаки и затухания гитары; остатки мужского голоса |

## 3. Уточнения экспертного плана

| Предложение | Решение для Dewiar |
|---|---|
| Одинаковый MP3-кодек гарантирует отсутствие сдвига | Нет. Нужны общая PCM-шкала, проверка decoder priming/padding и реальное переключение в WKWebView. Одинаковые параметры кодирования — необходимая часть выбранного пути, но не гарантия |
| По временам слов известно, где голоса нет | Это гипотеза: возможны пропуски, распевы, хор, эхо и приблизительные времена. Проверять предполагаемые паузы отдельно; недостоверные интервалы исключать из измерений |
| ASR показывает количество разборчивых оставшихся слов | Показывает совпадения гипотезы ASR с опорным текстом. Возможны галлюцинации и пропуск слышимого пения. Название метрики — «совпадения ASR», а не «разборчивость» |
| Минусовка должна иметь громкость оригинала | Удалённый голос уменьшает общую энергию. Не выравнивать интегральную громкость дорожек автоматически; сохранять масштаб сопровождения и общий запас по пикам |
| `mix ≈ inst + vocals` доказывает качество | Для `inst = mix − vocals` это тождество, даже при плохом разделении. Для независимо предсказанных дорожек — диагностическая величина, не универсальный порог качества |
| Корреляция нашла сдвиг — исправить | Разный состав звука может давать ложный максимум. Исправлять только подтверждённый постоянный технический сдвиг; при неоднозначности не сдвигать автоматически |
| 16 кГц или один канал — отказ | Моно само по себе не запрет. Для узкополосной записи дать предупреждение о качестве и обработать доступный оригинал. Отказ — при повреждённом/пустом файле или техническом ограничении |
| Lossless → захват Яндекса → YouTube — порядок качества | Контейнер и сервис не определяют качество исполнения. Lossless-копия сжатого потока не восстанавливает детали. Сравнивать конкретные записи; не подменять версию песни |
| Сразу все модели, ансамбли, три формулы и suppressor | Сначала два кандидата на трёх записях, затем выбранные рецепты на всех девяти. Дополнительная обработка — только для выявленной проблемы |
| Час пользовательского прослушивания обязателен | Слепое A/B полезно, но не блокирует поставку. Техническая проверка, музыкальное прослушивание и предпочтение пользователя — три отдельных поля. Если прослушивания не было, честно показывать это |

Проверка исходников `audio-separator` выявила ещё три существенных условия:

- В рассмотренной ревизии `0.48.0` для Darwin arm64 действительно задан `torch >=2.13,<3`. Это требование конкретной ревизии, а не всех версий разделителей. Закрепить проверенную сборку с зависимостями, не устанавливать плавающий `latest`. [Метаданные пакета](https://github.com/nomadkaraoke/python-audio-separator/blob/4dd3477c0a8f5bfb0fb053c6ed444bb935cb150e/pyproject.toml).
- `normalize()` уменьшает сигнал при превышении верхнего порога; усиление зависит от нижнего порога. Это не постоянное приведение каждого файла к 0,9. Нужно контролировать все места вызова и фактические коэффициенты. [Реализация normalize](https://github.com/nomadkaraoke/python-audio-separator/blob/4dd3477c0a8f5bfb0fb053c6ed444bb935cb150e/audio_separator/separator/uvr_lib_v5/spec_utils.py).
- Экспорт через pydub сначала преобразует массив в int16. Поэтому рабочий выход — WAV FLOAT через `use_soundfile=True` с проверкой subtype, затем собственная финализация FLAC PCM_24. Расширение `.flac` само по себе не гарантирует отсутствие промежуточной потери точности. [Реализация экспорта](https://github.com/nomadkaraoke/python-audio-separator/blob/4dd3477c0a8f5bfb0fb053c6ed444bb935cb150e/audio_separator/separator/common_separator.py).

## 4. Подготовка минусовки: алгоритм

### 4.1. Зафиксировать исходник

1. Разрешить только файл, принадлежащий текущей песне внутри `SongStore.root`; проверить реальный путь, читаемость и свободное место. В worker не передавать произвольные пути из браузера.
2. Запомнить SHA-256 содержимого, размер, фактический формат, число сэмплов, каналы, длительность, версию конвейера. Хэш повторно проверять перед публикацией, если файл менялся во время работы.
3. Измерить sample/true peak, ориентировочную полосу, уровни, корреляцию каналов; отсутствие энергии наверху не считать доказательством конкретного кодека. Уже повреждённые пики исходника фиксировать отдельно.
4. Использовать именно текущую запись. Другой источник того же названия автоматически не подходит. Более качественное переиздание может иметь другой монтаж, скорость или начальную тишину; его замена — отдельная операция с повторной проверкой таймингов.

### 4.2. Общая временная шкала

Декодировать один раз в float32. Для первого рецепта — 44 100 Гц, два канала, без нормализации, обрезки тишины, шумоподавления и изменения темпа. При доступном soxr использовать закреплённые параметры; иначе проверенный FFmpeg-ресэмплер с записью реализации в manifest.

`canonical_samples` — фактически полученная длина этого PCM, а не округлённое `audio.duration_ms`. Все дорожки и версии для плеера строить из этой шкалы. «До сэмпла» относится к одинаковой частоте canonical PCM; напрямую сравнивать количество сэмплов 48 и 44,1 кГц нельзя.

Моно дублируется только для входа модели; мастер возвращается к исходной моно-топологии. Если модель требует другую частоту, её ресэмплинг и возврат в canonical-шкалу входят в рецепт и проверки.

Для пилотных 30-секундных отрывков подавать реальный контекст до/после (начальное значение 10 с, в пределах файла), оценивать центральный участок. Тишина по секунде на краях не объявляется универсальным улучшением: сначала проверить поведение адаптера. Полную песню обрабатывать штатными перекрывающимися окнами модели; не склеивать независимо обработанные фразы.

### 4.3. Два первых кандидата

**A: существующая HTDemucs 955717e8**, прочитать уже скачанные веса. В пилоте сравнить `mix − vocals` и сумму `drums + bass + other`. Восстановление масштаба после внутренней нормализации адаптера проверять отдельно; не считать текущий probe окончательным эталоном.

**B: одна локальная MelBand/BS-RoFormer для удаления вокала.** Первый проверяемый кандидат — Kim FT2 Bleedless из экспертного плана. До скачивания подтвердить точное имя весов, YAML, источник, ревизию, лицензию и совместимость с закреплённым runtime. При недоступности — проверенная BS-RoFormer Viperx; подмена рецепта фиксируется в отчёте. Имена и рекламные метрики из обзора не считать подтверждённым реестром.

Сначала сравнить на «Правда ведь, обидно», «Планы» и «Папа — Соня и Маруся»: архив, гитара, два голоса. Успех пилота — не просто завершение процесса, а сохранность музыки, отсутствие явной утечки слов и приемлемые ресурсы. Затем полные девять записей; для проблемных треков допускается другая модель.

Параметры: начать с рекомендованного YAML, batch size 1; сохранять фактические chunk/overlap/precision/device/seed. MPS сравнить с CPU на одном фиксированном фрагменте по конечности, длине, уровню, разности и прослушиванию. Универсального требования «разность ниже −60 дБ» не вводить. При OOM — уменьшать batch/chunk в разрешённых моделью пределах либо CPU; уменьшение overlap не считать гарантированным лечением памяти.

**После пилота, по необходимости:** один suppressor для остаточного голоса; отдельный «fullness» кандидат при потере гитары; ансамбль только при измеренной и слышимой пользе. Фазовая замена STFT не входит в MVP: нельзя обещать восстановление инструментов без дополнительных артефактов. Вариант «с бэком» также отдельный рецепт: удаление солиста не равно удалению всех ведущих голосов. [Описание lead/back моделей MVSEP](https://mvsep.com/algorithms/76).

### 4.4. Масштаб, границы и финализация

- Рабочие массивы и файлы — float32. Адаптер должен сохранять масштаб или возвращать каждый применённый gain. Если библиотека нормализует выход без обратимого учёта, доработать адаптер; не пытаться восстановить потерянный масштаб исключительно по сомнительным паузам.
- Удалять только известный технический padding. Нельзя маскировать неожиданную потерю хвоста безусловным `pad/truncate`: расхождение с контрактом модели — ошибка проверки. У результирующего мастера `sample_count == canonical_samples`.
- Проверить смещение и дрейф в начале, середине и конце на сопоставимых музыкальных событиях. При отсутствии надёжных опор — `alignment_check: inconclusive`, не выдумывать измеренный ноль. Дополнительно проверять механику на отдельном тестовом сигнале.
- Для original/instrumental рассчитать общий статический коэффициент ослабления с запасом, стартовый ориентир −1 dBTP. Проверять true peak после кодирования и декодирования MP3: кодек может добавить межсэмпловые пики. При необходимости увеличить общее ослабление. Не применять независимый loudnorm, компрессор или усиление тихой минусовки по умолчанию.
- Диагностические LUFS/RMS сохранять, но интегральный LUFS минусовки не обязан равняться полной смеси. На подтверждённых участках без вокала отклонения уровня/спектра помогают выявить потери музыки, не являются основанием автоматически усилить всю дорожку.
- Мастер — FLAC PCM_24 после проверки пиков; оригинал остаётся исходным файлом. Для плеера — согласованная пара MP3 из canonical-шкалы с общим gain; параметры кодера и версии инструментов входят в ключ кэша.
- Если обе дорожки получены из `mix − vocals`, сумма проверяет лишь арифметику адаптера. Для двух независимых выходов остаток суммы хранить как диагностику, без универсального pass/fail −30 дБ.

### 4.5. Музыкальная проверка

Автоматический отчёт отдельно от вердикта прослушивания:

1. **Технические ошибки:** NaN/Inf, пустой результат, недопустимая длина, неучтённый сдвиг, клиппинг, потеря каналов. Не публиковать как готовый вариант.
2. **Сохранность музыки:** вручную или надёжно подтверждённые невокальные интервалы; пометка источника границ. Сравнить энергию/спектр и атаки. Если таких интервалов нет — `not_applicable`, не нулевой балл.
3. **Остатки голоса:** ASR без подсказки текстом на выбранных вокальных интервалах; временно упорядоченное сопоставление с проверенной частью текста. Сохранить N совпадений, M опорных слов, покрытие и гипотезу. Проверить фон на невокальных интервалах и чувствительность распознавателя на оригинале. Если на оригинале он ничего не распознал, ноль на минусовке не информативен.
4. **Прослушивание:** гласные, согласные/шипящие, эхо, оба голоса дуэта, гитарная атака, тарелки, провалы и «водянистость». Начало, куплет, плотный вокальный участок и конец; для 46 с — неперекрывающиеся короткие участки и вся запись, а не четыре независимых 20-секундных отрывка.

Повторное разделение инструментала другой моделью — дополнительная диагностика финалистов, не обязательный третий дорогой прогон каждой песни. Модель может принять инструмент за вокал.

Записывать `technical_status`, `quality_status: unreviewed|acceptable|defects|unsuitable`, замечания, проверившего и дату. Автоматический анализ не имеет права ставить `listened_by: user`. Если у исполнителя проверки нет возможности прослушать звук, готовить реальные A/B-файлы и оставлять `unreviewed`, продолжая внедрение. Прослушивание пользователем и выбор предпочтения доступны, но обязательного часа участия нет.

## 5. Архитектура службы и хранения

### Отдельная задача и очередь

Новые небольшие модули в `core/songs/`:

| Файл | Ответственность |
|---|---|
| `instrumental.py` | `InstrumentalManager`: проверка входа, очередь, идемпотентный запуск, отмена, публикация, события |
| `instrumental_store.py` | Отдельный manifest, revision, атомарные записи, read-only summary и восстановление |
| `separation_runtime.py` | Поиск внешнего Python, запуск worker, прогресс, завершение только своего процесса |
| `separation_worker.py` | Канонический PCM, адаптер модели, разделение, технические проверки; без Engine/STT/TTS/LLM |
| `audio_variants.py` | Проверенное разрешение variant → артефакт, кэш MP3, общая шкала и gain |
| `resources.py` | Общий отменяемый шлюз тяжёлых фоновых музыкальных задач |

Состояния выполнения: `absent → queued → preparing → separating → checking → ready`; ответвления `cancelled`, `failed`, `interrupted`, `stale`. Оценка качества отдельная. При повторной подготовке старый выбранный результат остаётся доступным; поля `active_job` и `selected_candidate` независимы.

`run_id` и хэш исходника проверяются при каждом завершении; поздний результат отменённой/заменённой задачи не выбирается. Дубликат того же ключа возвращает существующий job или готовый кандидат. Отмена во время очереди не запускает модель; во время обработки завершает только принадлежащий задаче process group с ограниченным ожиданием. Декодирование и финализация тоже отменяемые.

После перезапуска незавершённый job получает `interrupted`; проверенные результаты сохраняются. «Повторить» создаёт новый run. Не обещать продолжение посреди нейросетевого окна. Уже готовые элементы пакета переиспользуются, оставшиеся видны отдельно.

Общий шлюз вводится для внешнего музыкального ASR, align/chords и separation; базовое распознавание SongAnalyzer тоже должно получать его. Не держать его при вызове операции, которая захватывает его повторно. Он не останавливает обычный плеер и не меняет глобальные настройки голосового помощника. Реальная свободная память проверяется с учётом уже работающих моделей.

### Файлы и контракт данных

```text
STATE/songs/<song_id>/karaoke/
  manifest.json
  runs/<run_id>/job.json, progress.json, worker.log
  candidates/<cache_key>/instrumental.flac, vocals.flac, checks.json
  playback/<pair_key>/original.mp3, instrumental.mp3, metadata.json
```

Manifest schema v1:

```json
{
  "schema_version": 1,
  "revision": 1,
  "source": {"sha256": "...", "sample_rate": 48000, "sample_count": 0, "channels": 2},
  "timeline": {"sample_rate": 44100, "sample_count": 0, "origin_ms": 0},
  "active_job": {"run_id": "...", "state": "queued", "stage": null, "progress": null},
  "selected_candidate": null,
  "candidates": [],
  "presentation": {"variant": "original"}
}
```

Здесь нули — заполнители схемы, не допустимые длины готовой дорожки. Для кандидата обязательны: ID, source hash, pipeline version, model/revision/weight+YAML hashes, runtime lock hash, параметры/seed/device/precision, sample counts, технические коррекции, gain, checks, quality/listening, artifact hashes, время, пик памяти и размер.

Ключ результата: source hash + preprocessing version + model/YAML hashes + параметры/precision + formula + pipeline version. Ключ выдачи включает оба выбранных мастера, общий gain, encoder version/settings. Версия текста входит только в диагностику ASR, а не в ключ разделения.

Писать во временный каталог на том же диске, проверять и атомарно публиковать manifest после артефактов. При сбое между файлами и manifest остаётся невыбранный каталог, который можно безопасно убрать позже. Progress хранится вне `song.json`: не увеличивать revision текста и не раздувать `edits`.

В список карточек передавать только состояние, наличие варианта, оценку, краткий прогресс/ошибку. В `public.py` добавить разрешённый summary `karaoke`; сырые гипотезы, пути, логи и manifest целиком не выдавать. Через команды получить подробности по необходимости.

Исходник и пользовательские правки не перезаписывать. Смена записи делает старый кандидат `stale`; правка текста не делает. Удаление карточки/замена аудио/начало новой записи должны учитывать активную задачу минусовки. «Удалить минусовку» удаляет только её собственные артефакты после остановки; файлы кэша модели и оригинал не затрагивает. Проигравшие кандидаты удалять явной очисткой, не сразу автоматически. `vocals` — отладочный артефакт, его очистка не должна удалять выбранный инструментал.

Оценка диска — по фактическим размерам плюс временные файлы. FLAC имеет переменное сжатие; не обещать фиксированные 9–10 МБ/мин. Float32 stereo 44,1 кГц требует около 20,2 МиБ/мин на каждый несжатый рабочий буфер/файл. Предварительно оценить пик для выбранного рецепта и прекращать новые задачи при нехватке места.

Событие `song_instrumental` содержит job ID и revision; список обновляет значки, не пересоздаёт активный `<audio>` и поля редактирования.

### Пакет из существующих песен

В «Задачи → Песни» выбор нескольких карточек → «Подготовить минусовки». Выполнять последовательно; одну ошибку показывать у соответствующей песни и продолжать следующие. Карточки без файла — `skipped: missing_audio`. Повтор пакета использует готовые результаты. Предусмотреть отмену текущего элемента и всего пакета; последняя не удаляет завершённые минусовки.

Состав и состояние пакета сохранять атомарно в `STATE/song_batches/<batch_id>.json`: список song/job ID, принадлежность запуска, пропуски, время и итог каждого элемента. Список из двухсот элементов не создавать как двести тяжёлых потоков — один диспетчер выбирает следующий job. Если готовая или уже запущенная отдельно задача переиспользована пакетом, отмена пакета отсоединяет её от ожидания, но не отменяет чужой запуск. При восстановлении показывать прежний пакет и незавершённые элементы; повтор запускает только их.

### Этап в существующей пакетной обработке медиа

Точки подключения: `ui/assets/transcribe-panel.js`, `core/engine_commands.py::media_transcribe`, `TaskManager.create_transcription/_run_media`, `core/media_transcription.py`.

- Добавить явную опцию **«Это песни: подготовить минусовки»**, выключенную для прежних/обычных речевых задач. Хранить в данных задачи, включить в ключ повторного использования задачи; старые задания не превращать в музыкальные автоматически.
- Доступ к полной записи выделить в переиспользуемую функцию получения аудио. Если текст взят из субтитров, аудио всё равно понадобится; если файл уже в `.media-cache`, не скачивать заново. Не брать для минусовки речевую копию 16 кГц.
- После получения файла связать результат с `song_id` по сохранённой связи и source hash. Одно название не критерий совпадения. При отсутствии карточки создать песню с сохранённой копией оригинала через общий импортёр. Повторный запуск не создаёт дубликаты.
- Отправить в тот же `InstrumentalManager`. Подготовка может идти после освобождения ресурса ASR; её успешность не зависит от наличия текста, аккордов или резюме. Не переносить в песню «очищенный» связный текст из речевого pipeline.
- В отчёте пакета раздельные результаты: расшифровка и минусовка; невозможность одного этапа не скрывает готовый другой. `instrumental_only` — отдельный явный режим на следующем шаге интеграции, не скрытое изменение `media_transcribe`.
- В существующем разборе песни `song_transcribe` добавить необязательное `prepare_instrumental`. Цепочка: полная запись → разбор → очередь минусовки. При неуспехе текста минусовку всё равно можно подготовить из сохранённого аудио. Для уже разобранных песен кнопка минусовки не вызывает ASR повторно.

## 7. Плеер и минимальный интерфейс

Около нынешних кнопок — `Оригинал | Минусовка`. Пока результата нет, второй вариант недоступен с объяснением и рядом действие подготовки. Во время подготовки доступны оригинал и отмена; показывать стадию и только реальный процент. Если есть прежний готовый результат, его можно слушать во время пересчёта.

Подсказки: «Воспроизводить сохранённую запись с голосом исполнителя»; «Воспроизводить эту запись без отделённого вокала; текст и аккорды остаются на прежних местах». Для `unreviewed/defects` рядом короткая отметка, подробности по раскрытию. Не показывать пользователю названия tensor/backend/precision в основном потоке.

### Безопасное переключение

1. Завести транспортное состояние: song ID, source revision, variant, позиция на шкале песни, желаемое playing/paused, request epoch. Кэш — не по одному song ID, а по source/artifact revision + variant + encoding/gain.
2. При переключении зафиксировать позицию, поставить звук на паузу и удержать подсветку. Первая загрузка может дать короткую паузу: бесшовный crossfade не обещается.
3. Получить `song_full_audio`. Принять ответ только для текущей песни, версии и request epoch. При ошибке сохранить прежний источник и позицию с явным сообщением, не включать автоматически другой вариант.
4. Установить src, дождаться metadata, применить проверенное преобразование `song_time ↔ media_time`, выполнить seek и дождаться его завершения/готовности. Удалить временные обработчики после успеха, ошибки или отмены. Ограничить время ожидания.
5. Возобновить только если актуальное намерение — playing. Стоп, пауза, новая смена варианта, смена песни и закрытие вида делают старый запрос неактуальным. Стоп во время загрузки не должен закончиться новым звуком.
6. Обновлять `SongSheet.updatePlayback` по шкале песни. Переходы по строкам используют ту же шкалу, не времена MP3 с неучтённым смещением. Оставлять `followSheet=false` при запуске из карточки согласно текущему поведению.
7. Прослушивание отдельных фраз для проверки текста остаётся оригинальным голосом. Этот режим явно подписан. Возврат к полной песне использует выбранный вариант; phrase src/loop не попадает в кэш всей песни.

Ограниченный кэш только активной песни, максимум два варианта; освобождение при закрытии/смене. Base64 имеет накладные расходы и копии в памяти, поэтому не обещать размер 4–6 МБ и мгновенный seek: измерить на WKWebView. Повторное переключение использует уже подготовленный файл без повторной нейросети/FFmpeg.

MP3 готовить в обычный seekable-файл, проверить его delay/padding metadata и браузерное декодирование. При необходимости — один измеренный offset на encoding profile в явном контракте. Если согласованная пара не проходит проверку ≤50 мс, сначала исправить формат/метаданные; не компенсировать произвольной задержкой подсветки. Новый медиасервер нужен только если текущий транспорт окажется ограничением. Записи >10 минут пока получают явное ограничение воспроизведения; подготовка мастера и лимит плеера — разные состояния.

## 8. Установка моделей без изменения рабочей конфигурации

Добавить `requirements-song-separation.lock`, реестр рецептов/весов и `tools/install_song_separation.py`. Runtime — `~/Library/Application Support/Dewiar/runtimes/separation/`; в dev допускается отдельный путь `DEWIAR_SEPARATION_PYTHON` по аналогии с ASR.

Установщик проверяет платформу, совместимость Python/torch, существующие веса и свободное место, затем устанавливает только выбранный рецепт в новое окружение. Данные ревизий и контрольные суммы фиксируются. Не заменять старое окружение, пока новое не прошло smoke-check. Готовые HTDemucs-веса читать из найденного кэша без гигабайтных копий.

`audio-separator` умеет автоматически скачивать отсутствующие модели. Одних Hugging Face offline-флагов недостаточно: в worker отключить/перехватить загрузчики, заранее проверить локальный реестр и тестом доказать отсутствие любых сетевых запросов. Установка — отдельное явное действие, не побочный эффект открытия карточки. [Описание загрузки моделей и API](https://github.com/nomadkaraoke/python-audio-separator#ensemble-support).

Worker запускается `-B`, с `PYTHONDONTWRITEBYTECODE=1`, очищенным PyInstaller-окружением, журналом в данных, а не внутри `.app`. Torch/модели не импортируются при старте основного приложения. Пакет `packaging/macos.spec` уже копирует `core` и `ui`; новый worker должен попасть в сборку, внешний runtime остаётся внешним. Доступный установщик для установленной `.app` нужно включить явно: весь каталог `tools` сейчас не копируется.

Исходники для сравнения на MVSEP не загружать. Локальные веса проверять отдельно от лицензии MIT на код. Наличие записи в рейтинге MVSEP не означает наличие локально доступной модели. [Таблица моделей MVSEP](https://mvsep.com/algorithms/34).

## 9. Этапы разработки и проверяемый выход

Оценки предварительные, пересмотр после замера моделей. Базовая поставка M0–M5 — ориентир 9–14 рабочих дней; сложная очистка отдельных песен может потребовать дополнительного времени и не имеет гарантированного результата.

| Этап | Работа | Условие завершения |
|---|---|---|
| M0, 1–2 дня | Закрепить runtime и второй рецепт, инвентаризация качества, пилот A/B на трёх записях | Есть реальные аудиорезультаты и отчёт: технические проверки, доступная оценка на слух, скорость/память. Выбраны рецепты для полного прогона |
| M1, 2–3 дня | Worker, canonical PCM, scale/padding, проверки, manifest, кэш | Целая реальная песня воспроизводимо даёт мастер и согласованную пару для плеера; ошибки не публикуются |
| M2, 1–2 дня | Manager, общая блокировка, отдельные состояния/отмена/recovery, команды | Можно запустить и отменить минусовку, редактируя текст без revision-конфликтов; прежний результат сохраняется |
| M3, 1–2 дня | Кнопка подготовки, original/instrumental в существующем плеере | Рабочий сквозной результат на одной песне в native WKWebView, pause/stop/seek и подсветка проходят проверки |
| M4, 2–3 дня | Выбор песен пакетом, интеграция опции медиа/разбора, реальные девять песен | Отчёт для всех девяти; пропуски карточек без аудио понятны, повтор не пересчитывает готовое |
| M5, 2 дня | Регрессии, чистая сборка, проверка подписи, обновление `.app` | Та же функция проверена в установленном приложении; настройки, голоса, исходники и правки сохранены |

Внутри M4 разрешено сначала выпустить пакет по существующим карточкам, затем опцию в медиа-обработке, но итоговая приёмка включает оба согласованных способа запуска. Отдельный экран слепого сравнения не задерживает первую поставку: пилот можно оценивать по подготовленным A/B-фрагментам и отчёту.

Тесты — адресные, в изолированных CONFIG/STATE/WORKSPACE; не запускать общий `unittest discover`. Подготовка плана не требует выполнения моделей или изменения установленной программы.

| Уровень | Что проверить |
|---|---|
| PCM/адаптер | 44,1/48 кГц, моно/стерео, тишина/короткий файл, точное число сэмплов, известный padding, сохранение канального порядка, NaN/Inf, отсутствие неучтённой нормализации и int16-промежутка |
| Метрики | Неполный текст, estimated timing, пустой ASR на оригинале, галлюцинация на музыке, отсутствие невокальных интервалов: нет ложной отметки «вокал удалён» |
| Хранение | Атомарность, сбой до/после manifest, дубликат запуска, source changed, старая revision, path traversal/symlink за пределы принадлежащего каталога; обычная правка текста не требует нового разделения |
| Очередь | Отмена в ожидании/декодировании/разделении/проверках; общий ресурс с ASR; после рестарта interrupted; поздний worker не выбирает отменённый результат |
| Транспорт | Реальный JSON с base64 ниже лимита 16 МиБ, 600-с граница, превышение лимита, FFmpeg timeout, файл исчез; неизвестный вариант не превращается молча в original |
| JS-плеер | A→B→A быстро, switch+pause, switch+stop, смена песни, detached DOM, error/ended/loop, предыдущая/следующая строка, отмена подготовки, нет двух звуков и самозапуска |
| Пакет | Существующий кэш, только субтитры без аудио, один плохой файл среди хороших, карточка без аудио, повтор/отмена, отдельные результаты текста и минусовки |
| Реальные записи | Девять полных файлов, включая короткий архив и оба дуэта; сначала/середина/конец; сохранность гитары и остатки вокала описаны по каждой записи |
| UI | Native WKWebView и браузер: 375/800/1440 px, обе темы, подсветка/прокрутка, соседство аккордов с текстом и «Проигрыш», копирование/транспозиция без регрессий |
| Установка | Проверка отсутствия сетевых загрузок при открытии и работе; исходники/настройки/голоса до и после; `codesign --verify --deep --strict` после реального worker |

Технические критерии: равенство длин canonical-мастеров до сэмпла, отсутствие неучтённого технического сдвига, отсутствие новых клиппированных отсчётов, контроль true peak выдаваемого звука. Браузерный seek — целевое расхождение ≤50 мс в измеренных контрольных точках; это точность переключения дорожек, а не подтверждение точности распознанных слов. Одного совпадения `currentTime` мало: добавить декодирование/контрольные события и native-прослушивание.

Музыкальные критерии: явные разборчивые слова или заметная потеря гитары означают `defects/unsuitable`, а не автоматическое «успех». Пользоваться технически готовым результатом можно с этой отметкой. Улучшенный рецепт не подменяет уже выбранный пользовательский вариант без выбора. Непроверенное прослушиванием остаётся `unreviewed`.

Расширить существующие `tests/song_playback_js_test.cjs`, `tests/song_cards_ui_test.py`, `tests/song_pipeline_unittest.py`, `tests/media_batch_ui_test.py`; добавить сфокусированные тесты instrumental store/manager/worker и переключения вариантов. Для регрессии листа использовать уже имеющийся `tests/song_sheet_layout_ui_test.py` на всей реальной библиотеке. Синтетический звук проверяет только механику, не музыкальное качество.

Артефакты приёмки: инвентаризация с хэшами, закреплённый рецепт, отчёт по девяти песням, реальные A/B-примеры, runtime/resource log, browser/native результаты, журнал сборки/подписи, сравнение сохранности рабочей конфигурации. Не включать в git пользовательские аудио, модели, токены и абсолютные личные пути. Коммит реализации и обновление приложения выполняются после этих проверок.

## 11. Первый конкретный шаг после согласованного плана

Создать изолированный benchmark подготовки минусовки с сохранением отчёта по трём песням. Сначала существующая HTDemucs без скачивания; затем одна проверенная RoFormer в новом runtime. Получить сопоставимые фрагменты и замеры, подтвердить масштаб/тайминг и качество сопровождения. По результату закрепить основной рецепт и сразу строить сквозную цепочку «кнопка → задача → готовая минусовка → существующий плеер». Остальные модели добавлять по конкретным дефектам, не до появления работающего результата.
